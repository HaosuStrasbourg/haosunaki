# HaosuNaki 设计基准

确认日期：2026-10-03。依据：用户对推荐稿 01 回复“整体可以”；在「HaosuNaki 平铺评审 02」进一步逐项确认 1C 描边、2A 冷静扩展、3A 蓝白珊瑚数值色阶。精修案例的具体构图、线宽、圆角及组件细节未随配色一并确认。英文正文沿用桌面 19px／32px、手机 18px／30px。后续用户明确：图表逐张判断目的，只有明确突出单一对象时使用蓝＋灰；平等比较使用分类配色。

组件与排列细则见 [组件与排版补充](2026-10-03%20-%20组件与排版补充.md)。默认标题、控件、内容与图注共用 720px 阅读宽度；1120px 宽版心仅用于复杂内容确有需要的独立区段。宽版心与 664px 卡片换列阈值为可调整工作建议。

适用：AI 生成的阅读型 HTML、个人静态内容页及按实际内容校验后的打印版。目标是快速抓住结论，再按需深入阅读；气质克制、现代，有留白。内容页不加署名、Logo 或系统名称落款。设计规范页可以标明 HaosuNaki，方便识别规范。

更新：2026-10-04 组件评审 02 最终版通过。中性辅底统一更新为 `#F4F1EC`，建议提示底为 `#F5F6FB`；已确认组件的紧凑字级、边界及状态范围优先见[已确认组件与组合](2026-10-04%20-%20已确认组件与组合.md)。下列长文基准不强制继承到紧凑组件；旧实现资源仍需逐项迁移和验证。

## 1. 内容结构与可变部分

优先采用：标题 → 一句结论 → 必要的关键数字 → 图表与解读 → 详细依据。各部分按真实内容取舍，不强制每页填满所有组件。

- 标题传达主题；结论回答读者最想知道的问题；正文交代依据和条件。
- 只有资料支持时才制作数字卡、趋势图和比较图。来源、单位、计算口径与限制靠近相关内容。演示数据显著注明“虚构演示”，不可冒充研究结果。
- 图解承担解释关系、步骤或差异的工作。普通正文已足够清楚时，不为了装饰添加图。
- 英文副标题、双语正文、流程、比较表、方法附录均为可选；不重复铺陈同一个结论。
- 摄影题材与固定图标库仍按内容选择。2026-10-05 插画已确认 A 细线编辑用于正文、C 纸感拼贴用于封面和大幅开篇，详见[插画风格与生成](2026-10-05%20-%20插画风格与生成.md)。保留来源记录，避免纯装饰占据首屏；插画不替代精确数据与机制图。

内容、章节数量、图表类型与具体布局可以变化。品牌色、五个字体用途和阅读层次是默认基准；专项要求产生的例外应说明，不自动改写整套规范。

## 2. 色彩角色

2026-10-04 用户确认通用原则：**业务含义、冷暖关系和类别区分，优先于品牌配色。需要明显区分时，不使用相近颜色硬凑。** 先判断颜色编码什么，再选择色相、明度和透明度；在实际底色、尺寸及叠加状态下核对可辨性。颜色同时配合名称、数值、符号或线型。

有明确领域含义时使用对应配色：本用户的金融阅读采用红涨绿跌，不视为全球统一约定；K 线比较当期开收盘，收益图须另写清相对前收盘或其他基准。温度等冷暖变量保持相应冷暖关系，连续色阶的中间色不自动等于零或冷热阈值。领域色不需要迁就默认品牌色集合。

| 角色 | 色值 | 使用方式 |
| --- | --- | --- |
| 纸白／页面底色 | `#FAF8F4` | 默认阅读背景 |
| 区块辅底 | `#F4F1EC` | 引用、指标整组、表头等必要分组 |
| 建议提示底 | `#F5F6FB` | 建议／结论提示，配钴蓝标题与细左线 |
| 正文 | `#282623` | 主体文字 |
| 辅助文字 | `#68635D` | 图注、标签、次要系列 |
| 分隔线 | `#D7D0C6` | 边框与轻分隔，不用于小字 |
| 钴蓝 | `#244AC7` | 链接、活动选项、关键数字和图表重点 |
| 陶珊瑚 | `#C45C46` | 分类辅色 |
| 莓红 | `#A33C62` | 另一分类辅色 |

正文重点优先用少量字重表达，不将整段文字染成强调色。链接同时保留下划线，键盘焦点有可见轮廓。大面积颜色保持克制，不要求每页集齐所有颜色。

**图表逐张明确语义，不设置整篇统一模式。**

- `focus`：已明确关注单一对象且没有领域色义冲突时，主要对象默认钴蓝，参照对象用辅助文字色。已有涨跌、类别或温度颜色不得被强调色覆盖；可用线宽、标注等非颜色方式强调。保留名称、数值和单位。
- `category`：按需要的区分度选择颜色，再与稳定对象 ID 绑定；不强制使用前三色，少于四类也可从默认集合选择合适颜色。需要明显区分时避免相近色相；默认集合不足可补充颜色或采用领域色，并在实际尺寸检查。跨图、重排及筛选不改变已有对象颜色；保留直接标签或图例。
- 没有明确重点时不自动使用 focus；每张图自身设置模式，同页可以混用。分类颜色绑定稳定类别身份，不能按排列位置分配。
- 同一数据编码不混用重点、分类与数值色阶。复合图的不同面板可以有不同编码，但须分别说明。比较前先确定数据范围与共同尺度；不得用装饰性刻度、截断柱轴等方式夸大差异。
- 陶珊瑚和莓红不自动代表错误、亏损、警告或风险。审阅／任务状态采用已确认组件参考中的映射；新业务仍需定义文字和视觉语义，不能挪用为金融涨跌等通用色义。

当前色值在当前底色上的用途已有样张参考；新增底色、反白文字或图层叠加时重新检查对比度。不得以既有样张检查代替整个新页面的无障碍验收。

### 2.3 无特定领域色义时的默认数值色阶（原 3A）

以下默认值适用于没有明确领域色义的量值；金融涨跌、温度冷暖等优先服从本节开头的配色原则。

| 数值语义 | 色值，按数值从低到高 |
| --- | --- |
| 单向数量，从少到多 | `#EDF1FC` → `#C3CFF3` → `#91A6E6` → `#5678D6` → `#244AC7` |
| 相对基准偏差，从负到正 | `#244AC7` → `#91A6E6` → `#FAF8F4` → `#E5AB9F` → `#C45C46` |

- 顺序色阶用于数量、密度、强度等有序值，不用于平等类别身份。范围、单位和分级界限在图内可见；样张中的 0–100 不是通用固定范围。
- 发散色阶用于有真实基准的偏差。中心和两端范围明确，同组可比较时尺度一致；无特定色义时默认负蓝、零纸白、正珊瑚，不自动意味着坏/好、亏/盈。温度等没有偏差零点的有序量可用冷暖连续色阶，不得把过渡色虚称为真实零点。
- 同一组可比较图、筛选前后沿用共同尺度；如任务确需改变范围，必须明确标出。缺失显示「未提供」或独立纹理，不能涂成零值色。
- 五个锚点不是现成的通用插值引擎。按数据明确采用分级或连续插值，检查量值顺序、阈值边界和图例；渲染器未提供某种图时仍需定制并测试。
- 瀑布图等增减图按业务含义及该图已确认口径配色，保留 −／+、文字与图例；没有特定色义或个案确认时才采用负蓝、正珊瑚的默认方案。期初／期末保持中性；涨跌、好坏、收支及阅读重点不可自动等同。

配色获用户确认不等于完成色觉差异、反白字、叠加或印刷验收。文字尽量放在纸白上；填充单元内的文字需逐色检查对比度，陶珊瑚块避免常规小号白字。其他设备字体和 PDF 仍需按产物实测。

## 3. 字体、字号与混排

### 五个用途

| 用途 | 首选字体 | 缺失时的回退 |
| --- | --- | --- |
| 中文标题 | Songti SC | 本机 Noto Serif SC／Source Han Serif SC，再到 serif |
| 中文正文 | PingFang SC | 本机 Noto Sans SC／Source Han Sans SC，再到 sans-serif |
| 英文标题 | IBM Plex Mono | monospace |
| 英文正文 | JetBrains Mono | monospace |
| 展示数字 | Georgia | 内嵌 Lora，再到 serif |

中英混排的标题字体栈中，IBM Plex Mono 放在中文标题字体之前；正文同理先放 JetBrains Mono，再放中文正文。将通用 serif／sans-serif／monospace 放在相应回退栈末尾，避免提前截断中文回退。

Georgia 用于指标、图表值、刻度、步骤编号等具有独立信息作用的数字。正文句子里的年份、数量与编号可随正文排版；不对全部数字做自动替换。正文用常规 400 字重，局部重点采用 500，避免以粗黑大段强调。

长文采用上表；已确认的紧凑组件正文采用 15/24、辅助说明 13/20 等完整密度组合，见[已确认组件与组合](2026-10-04%20-%20已确认组件与组合.md)。主要研究论证不因进入框内而变为小字；`.workflow p` 默认正文尺度，只有短提示显式使用 `.step-caption`。纯英文段落用 `.english-prose` 与 `lang="en"`，以应用英文正文尺度；混排正文使用中文正文尺度和混排字体栈。

### 字体文件与分发

- 两款英文首选字体与 Lora 以原始开源字体文件内嵌于 `assets/fonts.css`，完整许可保存在 `assets/font-licenses.html`，输出时一并保留。
- Songti SC、PingFang SC、Georgia 仅通过本机字体调用。此包不提供它们的字体文件，也不代表获得了再分发或 Webfont 授权。
- 中文回退字体只引用本机可用字体；缺少时由浏览器选择通用字体。没有内嵌完整中文开源字库，因此不承诺 Windows、Android 与当前 Mac 字形一致。
- 若需要跨设备完全一致的中文呈现，再选用官方完整的开源中文字库，保留许可并测试新文章字形覆盖。不可把仅覆盖样张文字的 Noto 切片复用为通用字库；不可把私有正文发往第三方字体子集接口。
- 许可与原始来源附在产物中。新加字体先核对该具体文件的官方许可；“已安装”“免费下载”不自动等于允许打包分发。

## 4. 布局、间距与组件

正文内容列最大 720px；桌面 `main` 外框最大 816px，左右各 48px 内边距。中等视口可降到 32px，手机左右 24px。主要间距档位为 8、12、16、24、32、48、64px；章节间距桌面 64px、手机 48px。少量光学校正可用其他数值，不强行改变内容关系。

一般内容卡片圆角 16px 属于旧工作建议；已确认组件使用各自圆角与边界，不统一套框，不使用明显阴影。表格和文本优先保持平静连续的阅读表面，不把每段内容都封进卡片。

| 内容 | 样式入口 | 使用要点 |
| --- | --- | --- |
| 页面标题 | `header.hero`、`h1`、`.english-title` | 英文副标题可省略 |
| 开篇结论 | `section.summary`、`.section-label`、`.conclusion` | 一句直接的核心判断 |
| 关键数字 | `.metrics`、`dl.metric` | 数值用 `dd`，标签用 `dt`；数据不足时省略 |
| 正文章节 | `section.part`、`h2`、`.prose` | 每段承担独立信息作用 |
| 英文正文 | `.english-prose` | 添加 `lang="en"` |
| 比较图 | `.chart`、`.chart-row`、`.chart-meta`、`.track`、`.mark` | 逐图设 `data-chart`；focus 的唯一重点行用 `.primary`；category 指定稳定类别与颜色；`--value` 为真实比例 |
| 图表解读 | `figcaption.caption`、`.chart-note` | 说明单位、来源与解读边界 |
| 步骤流程 | `ol.workflow`、`.step-number`、`h3`、`p.output` | 桌面两列，手机单列；保留完整文字 |
| 简单比较表 | `.table-wrap > table` | 单元格写 `data-label`，供手机重排后显示列名 |
| 收尾问题或提示 | `.decision-note` | 确有下一步信息才使用 |
| 来源与附注 | `.article-footer` | 只放内容依据，不加个人署名 |

流程使用可重排的 HTML 文本；不得靠整体缩小大型 SVG 获得手机适配。步骤编号保持阅读顺序，必要时加连接关系。

简单三列表格在手机按每行堆叠，显示列标签并保留全部信息。真实二维矩阵若必须横向对照，可以单独设置局部横向滚动与明确提示，不强制堆叠；页面本身仍应正常重排。普通表格保留语义表头和 `scope`，图解提供可理解的文本描述。

交互按任务需要增加，不强制添加筛选器或工具栏。增加控件时，操作应有清楚标签、可见选中状态和键盘焦点；不要把推荐稿的配置侧栏复制到普通阅读成品。

## 5. HTML、GitHub 与 PDF

`scripts/build_html.py` 合成单文件 HTML，内嵌现有 CSS、开源字体与许可，本身无需联网。默认拒绝覆盖已有输出，`--force` 只适用于已授权的目标文件。正文自行加入的外部资源需另行处理，不应在此情况下宣称完全离线可用。

静态网页可以使用这套完整排版。GitHub 仓库中的 README Markdown 应保留结论层次、图片与表格，但不可承诺 README 会加载这些自定义 CSS 和字体。需要完整视觉效果时交付 HTML；发布或部署另按用户请求执行。

打印样式是 A4、17mm 页边距的起点，正文转为适合印刷的 pt 单位，隐藏操作界面。**v1 的屏幕样张通过检查，并不代表任意文章的 PDF 分页已经验证。** 用户要求 PDF 时，必须实际导出，检查标题孤行、卡片与图表跨页、表头和页边内容，再交付。

## 6. 新内容的最小检查

验收围绕实际内容进行，不需要复刻所有参考样张：

- 在桌面与手机查看首屏：结论能否快速找到，字形是否符合五个用途，章节是否留出足够空间。
- 在 390px 与窄至 320px 的视口检查重排：无非预期的页面横向溢出；流程、长标题和表格信息没有丢失。
- 核对图表来源、单位、比例计算和颜色语义；无数据时不出现虚构指标。
- 检查放大文字后是否遮挡或截断，特别是固定高度区块和交互控件。若只做了样式模拟，应明确记录方法，不称为浏览器真实缩放验证。
- 需要离线使用时，在禁止网络的条件下打开最终 HTML，检查字体回退和全部正文。跨设备未测试时明确说明。
- 若产物有交互，验证关键切换与状态；若交付 PDF，检查实际 PDF，而非只看浏览器打印样式。

## 7. 方法依据与 HaosuNaki 采用值

以下官方资料支持设计方法。HaosuNaki 的具体颜色、五字体组合与字号由个人样张选择产生，不是 Apple 或 IBM 的官方数值，也不表示得到官方认证。资料核对时间：2026-10-02。

- [IBM Carbon：排版策略](https://www.carbondesignsystem.com/building-blocks/foundations/typography/style-strategies)——区分操作界面与阅读表达的需求；采用阅读优先的思路。
- [IBM Carbon：字号角色](https://www.carbondesignsystem.com/building-blocks/foundations/typography/type-sets)——先定义用途，再选择字级；本规范的 20／36 中文与 19／32 等宽英文为 HaosuNaki 采用值。
- [IBM Carbon：间距](https://www.carbondesignsystem.com/building-blocks/foundations/spacing/overview)——使用有限尺度表达分组与层级。
- [IBM Carbon：颜色](https://www.carbondesignsystem.com/building-blocks/foundations/color/overview)——将颜色角色与具体色值分开。
- [Apple HIG：图表](https://developer.apple.com/design/human-interface-guidelines/charts)——使主要信息清楚，提供数据上下文。
- [Apple HIG：排版](https://developer.apple.com/cn/design/human-interface-guidelines/typography)——关注易读性与字号变化；未把原生平台 pt 数值直接当作网页 px。
- [W3C：重排](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)与[文字放大](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)——作为 320 CSS px 重排和 200% 文字放大检查的参考。
