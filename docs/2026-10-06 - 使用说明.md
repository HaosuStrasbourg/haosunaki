# HaosuNaki 使用说明

HaosuNaki 用于把已有初稿组织成可阅读、可比较、可解释的成稿。方法优先于样式：先明确读者任务与内容关系，再选择表达、组合组件、映射视觉参数并验证。默认主题是起点，可以按用途替换。

## 1. 准备与安装

运行要求为 **Python 3.10+**。三个核心 Python 脚本使用标准库，无需安装额外 Python 包。浏览 HTML 使用支持现代 HTML、CSS 和 JavaScript 的浏览器；这不是对所有浏览器或设备的兼容性保证。

不安装 skill 也能使用脚本：下载完整仓库，在仓库根目录运行本文命令。

若要在支持 skill 的助手中调用：

1. 下载并解压完整仓库，保留 `SKILL.md`、`references/`、`assets/`、`scripts/` 等目录的相对位置。
2. 找到宿主配置的个人 skill 目录，将完整仓库目录手工放入其中，目录名为 `haosunaki`。最终应能找到 `skills/haosunaki/SKILL.md`。
3. 若目标目录已存在，先备份并比较差异，再决定如何合并；不要直接覆盖现有安装。
4. 按宿主的 skill 加载方式启用，在请求中明确指定 HaosuNaki。

仅复制 `SKILL.md` 会缺少构建脚本和资源。安装 skill 也不会为宿主增加图像生成、浏览器控制或 PDF 导出能力。

## 2. 从初稿开始

先提供读者、阅读目的、输出格式以及初稿。已有数据、引用和图表应保留来源与口径；未知项注明待补。

```text
请用 HaosuNaki 整理这份初稿。
读者：[谁来读]
目的：[读完要知道什么、做什么]
输出：[HTML / PDF / GitHub README]
保留原意、数据和来源；缺失信息标注待补，不补造。

[粘贴初稿，或提供文件]
```

完整创作可按“明确目标 → 整理素材 → 搭建提纲 → 完成初稿 → 组织图文 → 复核修改 → 导出发布”推进。HaosuNaki 重点支持其中的组织图文环节：

| 步骤 | 需要做出的判断 | 检查点 |
|---|---|---|
| 理清主线 | 哪个结论最重要，依据、条件和背景如何排序 | 读者能找到结论及其依据 |
| 选择表达 | 哪些内容适合文字、表格、图形或交互 | 表达与读者问题、内容语义相符 |
| 组合排版 | 哪些内容属于同一组，如何对齐和强调 | 层级清楚，相同字段便于比较 |
| 验证呈现 | 内容、图形与操作是否一致 | 实际输出准确、可读、可用 |

准确字段比较优先用表格，量级比较可用条形图，时间变化可用折线图，步骤与条件用机制图。能用文字说清楚就不强行作图。图类选择见[选图判断树](../references/2026-10-04%20-%20选图判断树.md)。

## 3. 查看与构建 HTML

先将[图文使用说明](manual.html)或[演示页](../examples/demo.html)下载到本地，用浏览器打开。GitHub 文件页和 README 不执行 HTML / JavaScript，也不保证呈现网页中的字体与交互。

在仓库根目录生成演示：

```sh
python3 examples/build_demo.py
```

制作自己的页面时，先保存一个 UTF-8 正文片段，例如 `body.html`：

```html
<main>
  <header>
    <p class="eyebrow">方案说明</p>
    <h1>先写读者最需要知道的结论</h1>
    <p>说明结论成立的条件，并保留证据与未知项。</p>
  </header>
  <section>
    <h2>支持结论的依据</h2>
    <p>在这里放入正文、表格或内联 SVG。</p>
  </section>
</main>
```

再构建为独立 HTML：

```sh
python3 scripts/build_html.py \
  --body body.html \
  --title "方案说明" \
  --output report.html
```

构建器需要包含 `<main>…</main>` 的正文片段，不接收整份 HTML 文档。输入与输出不能是同一个文件，默认拒绝覆盖已有输出；需要替换时先确认目标，再使用 `--force`。

构建器会合入仓库的样式、所需脚本、开源字体与许可。正文可包含内联 SVG、定制样式和原生 JavaScript，但构建器不会自动下载或内嵌正文引用的外部图片、脚本等资源。要实现离线交付，正文也必须使用可离线取得的资源，并实际断网检查。

正文及脚本应来自可信材料；构建器不是 HTML 安全清洗工具。

## 4. 生成图形与选择参考

[`scripts/figure_primitives.py`](../scripts/figure_primitives.py) 提供三个高层函数，返回完整 SVG 字符串，由调用者决定保存或嵌入方式：

| 函数 | 输入与用途 | 主要边界 |
|---|---|---|
| `bar()` | 横向或竖向条形，比较量值、差距与排序 | 保留零基线；缺失不当作零 |
| `line()` | 数值横轴折线，展示连续顺序中的变化 | 缺失断线；不自动插值、平滑或补点 |
| `flow()` | 显式节点坐标与连线，解释步骤和机制 | 不自动布局或绕线，仍需检查图面 |

完整参数与调用示例见[图形工具接口](../references/2026-10-04%20-%20图形工具接口.md)。类别颜色按稳定对象 ID 绑定，不能随着排序或筛选改变；已有业务颜色语义优先于默认品牌色。图中的名称、单位、条件、缺失与来源必须能对应到正文。

[67 项官方参考 URL 索引](../references/2026-10-04%20-%20已确认图族与复用索引.md)按 10 类读者问题组织，用于选型与理解表达边界。本版不附这些案例的参考重绘 SVG，索引也不等于 67 个通用生成器。复杂统计、空间投影、定制布局和交互需按实际输入另外实现并验证。

## 5. 替换主题

颜色、字体、字号、间距、线条等共用参数集中在 [`assets/design-tokens.json`](../assets/design-tokens.json)。页面构建器和基础 SVG 工具读取同一来源。

修改前先判断影响的是基础值还是单一语义角色。例如强调色与类别色即使当前同色，也承担不同职责。换主题应保留对象身份、数据含义和阅读层级。

在仓库根目录校验参数、查看 CSS 映射：

```sh
python3 scripts/design_tokens.py --check
python3 scripts/design_tokens.py --mapping
```

然后重新生成受影响的页面与图形，并检查真实显示效果。已导出的文件是当次参数快照，不会自动换肤。主题修改也不自动重排复杂图、替换字体文件或更新插画。内部格式为 `haosunaki.tokens.v1`，不承诺完整兼容 DTCG。详细说明见[设计 Tokens 与参数维护](../references/2026-10-05%20-%20设计Tokens与参数维护.md)。

## 6. 插画与输出媒介

插画用于概念、气质与隐喻；精确数据、执行步骤和架构关系继续使用数据图或机制图。正文默认选择 **A 细线编辑**；封面、专题头图和大幅开篇可用 **C 纸感拼贴**。同组保持画风一致，不要求每页都配图。

本版保留[插画方法与提示词](../references/2026-10-05%20-%20插画风格与生成.md)，不分发 4 张插画参考 PNG。实际生成需要宿主提供图像生成工具，不能保证像素或色值精确一致。

| 输出 | 使用方式 | 交付前检查 |
|---|---|---|
| HTML | 本地浏览器阅读，承载图文与交互 | 桌面、窄屏、主要操作和离线资源 |
| PDF | 用合适的导出工具实际生成 | 分页、截断、字体、图注与打印尺寸 |
| GitHub README | 文字和静态图，另链接可下载的 HTML | 链接、静态图可读性及内容完整性 |
| SVG | 导出或嵌入静态图形 | 图内字体、标签、边界与目标显示尺寸 |

SVG 不保留页面交互，图外说明不会自动收入图形；PDF 导出也不保留完整 HTML 交互。本仓库的 HTML 构建命令不直接生成 PDF。

## 7. 检查与许可

运行基础检查：

```sh
python3 -m unittest discover -s tests -v
```

每份新成品仍须核对内容准确、重点清楚、图文一致和实际可读。长标签、边界数据、390px / 320px 窄屏、键盘操作及目标导出文件按实际使用场景检查。没有检查过的跨浏览器、手机、跨设备字体或 PDF，应明确标记为未验证；自动测试不能替代视觉验收。
