# HaosuNaki 使用说明

**把初稿交给 AI，整理成重点清楚、图文好读的成稿。**

## 一、HaosuNaki 是什么

HaosuNaki 是一套给 AI 使用的**图文表达框架**：帮助 AI 判断先讲什么、哪里需要图、内容怎样摆，再用统一的样式呈现。

你提供初稿、数据和阅读目标。AI 用这套 skill 整理成研究报告、方案说明、流程图或阅读型 HTML。核心方法可以复用。默认沿用 HaosuNaki 主题，需要定制时可统一调整配色和字体；组件按内容选择。

例如，写一份方案比较报告，读者应该先看到“推荐谁”，再看到条件和依据。HaosuNaki 就是把这条阅读顺序落实到文字、表格、图和页面里。

## 二、框架是什么

**四层各有分工，共同完成一份文档。**

| 四层 | 通俗地说 | 具体判断什么 |
|---|---|---|
| 决策流程 | 想清楚怎么讲 | 写给谁？读者要解决什么？结论和依据是什么？先看哪一部分？ |
| 表达库 | 提供表达办法 | 哪些组件适合查数、比较或解释？它们怎样组合？ |
| 视觉映射 | 让主次与关系看得出来 | 什么要突出？哪些属于一组？颜色、字号、对齐和间距怎么安排？ |
| 验收规则 | 检查是否讲对、能用 | 数据和条件有没有丢？图是否误导？页面和操作是否正常？ |

实际制作时，决策流程贯穿全程：**明确目标 → 整理内容 → 选择表达 → 组合内容 → 统一样式 → 检查成品。** 过程中调用表达库、应用样式，并随时核对。四层是职责分工，不是四道依次完成的工序。

选表达时，先看读者要做什么：

| 阅读任务 | 通常用什么 |
|---|---|
| 查准确数字，逐项核对 | 表格 |
| 看谁更多、差多少 | 条形图或点图 |
| 看随时间怎样变化 | 折线图 |
| 理解条件、步骤与关系 | 流程图或机制图 |
| 理解主题，建立直观印象 | 插画 |
| 尝试不同假设，看结果变化 | 有计算依据的交互图 |

文字负责讲清结论、原因和限制。图有助于理解时再加，不要求每一段都配图。

## 三、怎么用

在支持 skill 的助手中启用 HaosuNaki 后，**放入初稿，再说清读者、目的和输出形式。**

```text
请用 HaosuNaki 整理这份初稿。
读者：需要选择下一轮测试方案的负责人。
目的：看清表现和成本，决定先测试谁。
输出：HTML。
要求：保留原意、数据和来源，缺少的信息标注待补。

[附上初稿和数据]
```

初稿不必提前排版。有数据就附上单位、时间范围和来源；有成本上限、业务规则等条件，也一起说明。

AI 会安排内容、制作图文，你再根据成稿反馈。例如：“结论再靠前”“同一字段请对齐”“这里漏了失败分支”。数据与逻辑先改对，再调整样式。

HTML 适合阅读和交互；GitHub 适合文字与静态图；PDF 需要单独导出并检查分页。首次安装和自行构建的方法放在[操作附录](2026-10-06%20-%20安装与构建.md)。

## 四、细节 demo：从材料到成稿

### Demo 1 · 比较方案：先给建议，再让读者核对

初稿中的材料如下，数字均为**合成示例**：

> 三个方案各完成同一组 100 次任务。A 成功 68 次，B 成功 84 次，C 成功 75 次；单次成本分别为 1.0、1.6、0.8。成本不能超过 1.2，在合格方案中，优先继续测试本次成功率更高的方案。

**先判断**：这份报告要选下一轮测试对象。成功率和成本必须一起看，所以采用比较表，先放建议，再放证据。

成稿可以这样写：

> **建议：优先继续测试 C。**
> 成本上限为 1.2；在合格候选中，C 的本次成功率最高。

| 方案 | 成功次数 / 任务数 | 本次成功率 | 单次成本（演示单位） | 成本条件 |
|---|---|---|---|---|
| A | 68 / 100 | 68% | 1.0 | 符合 |
| B | 84 / 100 | 84% | 1.6 | 超过上限 |
| C | 75 / 100 | 75% | 0.8 | 符合 |

B 成功率最高，但成本超限。C 比 A 成功率高，且两者都符合成本条件，因此下一轮优先测试 C。

如果还需要快速看出成功率差距，再加一张图：

![三种方案的成功率：A 68%、B 84%、C 75%；合成数据](../examples/category.svg)

**这里的设计判断**：表格方便核对多个字段，条形图突出数量差距。三个对象平等比较，用可区分的类别色；结论仍要结合成本，不能只看最长的条形。已有类别色后，需要突出 C 时用标注或边框，保留对象原色。

**交付前检查**：分母一致、计算正确、成本条件保留。这组演示只支持“按当前规则继续测试 C”，没有证明 C 是实际最佳模型，也没有做统计显著性检验。

### Demo 2 · 解释流程：判断和分支必须看得见

假设需要解释：“初稿材料齐了就整理图文；没齐就先列出缺口。”

**先判断**：读者要理解一个条件分支，适合流程图。

![材料完整则进入图文整理，否则列出缺口、等待补充](../examples/flow.svg)

**这里的设计判断**：条件用菱形，出线标明“是／否”；开始与结束写清本段范围。普通节点保持白底，只给需要强调的节点加色。正式稿去掉调试编号，连线尽量短、少弯折。

**交付前检查**：两条分支都保留；“进入图文整理”不等于文档已经发布。更复杂的流程先补齐逻辑，再调整布局。

### Demo 3 · 组合页面：同一个问题的内容放在一起

![把零散内容组合成有主次的完整页面](images/composition-collage.png)

一张完整页面可以这样组织：

**标题 → 一句结论 → 比较条件与证据 → 理由和限制 → 下一步。**

比较表、引用块、结论框是**组件**；把条件、比较表和建议放在一起，就形成一个**方案比较组合**；多个组合再组成页面。

**这里的设计判断**：同一模块里的标题、图、图例与备注保持接近。不同模块用间距或轻量分隔区分，不必给每层都套边框。长文、表格、代码和图注使用不同密度，读者才能看出主次。

定制主题时，配色和字体可以统一替换，内容关系保持不变。业务含义与类别区分优先于品牌配色；“推荐”“已完成”和“当前选中”也要分别表达。

**交付前检查**：读者能否快速找到结论与依据，手机上是否读得清，图与备注是否仍在同一组。

### 需要交互时，先说明改变了什么

延续 Demo 1，如果要探索“预算改变后先测试谁”，才需要加入预算输入。图表、推荐和解释都应按同一规则更新：

| 成本上限 | 按示例规则得到的结果 |
|---|---|
| 0.7 | 没有合格候选 |
| 1.2 | 优先继续测试 C |
| 1.6 | 优先继续测试 B |

这是改变条件后的计算结果。固定比较不必增加控件；实际制作交互时，再检查这些输入是否得到对应结果。
