# HaosuNaki 使用说明

**把初稿放进来，让读者更快看懂：重点是什么，依据在哪里，哪些地方还不能下结论。**

HaosuNaki 是一套组织图文的方法，也带有可以直接使用的样式和生成工具。它会根据内容判断哪里用文字、哪里用表格、哪里需要图，再把这些内容组织成完整页面。

这份说明书先讲方法，再讲操作。只想开始使用，可以先读第一节；想了解系统如何判断，重点读第三至第七节；安装、构建与修改主题放在最后。

## 一、从哪里开始用

最直接的用法：**提供初稿，说明给谁看、希望读者看完知道什么或做什么。**

```text
请用 HaosuNaki 整理这份初稿。
读者：需要选择下一轮测试方案的研究负责人。
目的：看清三个方案的表现、成本和限制，决定先测试哪一个。
输出：可在浏览器打开的 HTML。
要求：保留原意、数据和来源；缺少的信息标注待补，不补造。

[粘贴初稿，或提供文件]
```

初稿不需要已经排版漂亮，但主要内容和逻辑应当写出来。有数据就一并提供数据、单位、统计范围和来源；已有比较条件也一起写上。例如“成本必须低于多少”“先看准确率还是先看速度”。

如果只给一句模糊的想法，助手可以帮助梳理，但那还包含内容创作和资料准备，不能把缺失的事实当作排版问题自动补齐。

完整的文档创作可以分为七步：

**明确目标 → 整理素材 → 搭建提纲 → 完成初稿 → 组织图文 → 复核修改 → 导出发布。**

HaosuNaki 主要在“组织图文”时应用，也为后续复核和导出提供规则。日常使用时可以把入口简化为下图：放入初稿，整理图文，复核成稿，再发布。

![从初稿到成稿：左边是文档工作流，右边展开 HaosuNaki 的内部工作](images/workflow.png)

图中实线箭头表示先后顺序；蓝色虚线表示把同一个环节放大说明。右侧是左侧 HaosuNaki 节点的内部细节，不是另一条额外流程。

## 二、先用一个例子把问题说清楚

下面用一个例子贯穿全文：**三个 AI 方案，下一轮先测试哪一个？**

所有数字都是为讲解而设定的合成数据，不代表真实产品。假设三个方案完成了同一组 100 次任务，成功标准相同，成本采用同一计量口径。

| 方案 | 成功次数 / 任务数 | 示例成功率 | 单次成本（演示单位） |
|---|---|---|---|
| A | 68 / 100 | 68% | 1.0 |
| B | 84 / 100 | 84% | 1.6 |
| C | 75 / 100 | 75% | 0.8 |

研究负责人给出的规则是：**成本不超过 1.2；在满足成本条件的方案中，优先继续测试本次成功率更高的方案。**

按这个规则，示例结论应当写成：

> 优先继续测试 C。B 在本组任务中的成功率最高，但超过本次成本上限；A 和 C 都满足成本条件，C 的示例成功率更高。

这句话不能扩大成“C 是最好的模型”。100 次示例任务没有证明统计显著性，也没有验证其他任务、延迟、稳定性或下一轮的表现。**图文应当让当前结论更容易理解，同时保留结论成立的范围。**

## 三、四层架构分别管什么

可以把 HaosuNaki 记成四个职责层：**决策流程、表达库、视觉映射、验收规则。**

| 职责层 | 用通俗的话说 | 主要回答什么 | 得到什么 |
|---|---|---|---|
| 决策流程 | 先想清楚怎么讲 | 读者要解决什么问题？该先看什么、后看什么？ | 一条有理由的内容与表达安排 |
| 表达库 | 提供可用的表达组件与组合 | 这里用文字、表格、数据图、机制图还是插画？几种内容怎样组合？ | 能完成阅读任务的组件与组合 |
| 视觉映射 | 让重要性和关系看得出来 | 哪个要突出？哪些是同类？哪些是说明？如何配色、对齐和留白？ | 层级清楚、风格统一的页面 |
| 验收规则 | 检查有没有讲错、看不懂、用不了 | 结论与证据是否一致？图有没有误导？实际输出是否可读？ | 通过项、需要修改的地方和未验证项 |

决策流程负责选择，表达库提供可选办法及使用条件。四层会相互配合。**决策流程安排整件事怎么做，过程中调用表达库，用视觉映射落实样式，并受到验收规则约束。** 因此，不能理解成先把“第一层全部做完”，再把“第二层全部做完”。

还要区分两种常见的“层”：

- **四个职责层**，说的是这套方法分别负责什么。
- **基础样式 → 组件 → 组合 → 页面**，说的是最终成品怎样组成。

例如，一张比较表是组件；比较表、结论提示和限制说明放在一起，构成一个“方案比较”组合；再加背景、方法与后续安排，组成完整页面。这个组成关系会在第五节进一步说明。

## 四、第一层：决策流程——每一步到底判断什么

这一层贯穿整个制作过程。通常会经过六个判断点；简单修改可以沿用已有决定，不必每次重新问完所有问题。

### 1. 明确任务：读者看完要得到什么

先判断读者是来了解情况、核对数据、比较方案、理解机制，还是实际执行操作。相同材料，目的不同，重点就可能不同。

本例的读者要决定下一轮先测试谁，因此既要看到成功率，也要看到成本门槛。如果目的只是介绍测试结果，就不应擅自加入“推荐 C”的决策。

**这一刻要定下来**：读者是谁、需要回答的问题、输出到哪里，以及已知的硬条件和偏好。硬条件是必须满足的门槛；偏好是在满足条件后用来排序的标准。

**本例产出**：“帮助研究负责人，在成本不超过 1.2 的前提下，选择下一轮优先测试的方案。”如果成本上限没有给出，助手应保留这个缺口，不能自己加一个门槛后假装是用户的规则。

### 2. 整理内容：哪些是事实，哪些是解释和条件

接下来把材料里的对象、数据、关系、结论和未知项分开。尤其要区分已经观察到的结果、对结果的解释、为了计算设定的假设，以及由公式得到的情景结果。

本例的 68%、84%、75% 是合成样本的计算值；“成本不超过 1.2”是决策条件；“优先继续测试 C”是按条件得到的建议。这三个角色不能混写。

还要判断这些数字能否直接比较：任务是否相同、成功标准是否相同、分母是否相同、时间范围和成本口径是否一致。如果不一致，应补充说明、拆开比较，或暂缓结论。

**本例产出**：一份完整比较材料，保留成功次数、任务总数、成本口径和判断条件；未知的统计显著性、延迟等明确保留，不用空白或零掩盖。

### 3. 选择表达：读者需要“查”还是需要“看”

准确查一个字段时，表格往往更直接；想迅速看出差距或趋势时，图更合适；解释原因和限制时，文字不可省。不是每段内容都需要一张图。

本例同时比较成功率、成本和资格，主表达采用表格。若还想让读者快速看出成功率差距，可以补一张条形图，但这张图必须与成本条件一起阅读，不能单凭最长的条形得出推荐。

**本例产出**：“一句建议 + 一张比较表 + 一段依据与限制”；条形图是按阅读需要加入的辅助表达。只有三行数据、一个固定结论时，不需要为了显得高级而增加切换按钮。

### 4. 组合组件：哪些内容应该放在一起

现在判断内容的归属和阅读顺序。属于同一个论点的标题、图表、图例、来源与备注，应当保持接近；不同任务段落则需要清楚分隔。

本例先给出“优先继续测试 C”，紧接着说明成本规则，再给比较表和依据。限制说明放在结论或证据附近，避免读者读完很久以后才发现结论有条件。

**本例产出**：一个完整的比较模块。它不是几个彼此无关的卡片，也不需要给每一句话都套边框。组件的职责清楚，比卡片数量多更重要。

### 5. 映射样式并实现：怎样让关系一眼可辨

到这一步才落实字号、颜色、表面、边界、对齐、留白和必要交互。依据是内容的作用：结论需要容易找到，说明需要归属于主内容，相同字段需要方便比较。

本例的推荐结论可以适度突出；“成本超限”用明确文字表达。若图表用于平等比较三方案，就为三者保持稳定的类别身份；若某张图只解释 C 的位置，可以用标注、边框或线宽突出 C。已经建立的类别色应当保留；没有既定类别或领域色义时，才采用蓝灰重点模式。

**本例产出**：可以实际打开的页面。若做交互，选择了哪个方案、正在查看哪组数据，都只是界面状态；它们不能被写成方案已经测试完成或已经采用。

### 6. 验证：页面是否兑现了前面的安排

最后复核结论、数据、图形、阅读顺序和操作。发现问题后，按原因回到对应环节，而不是一律改颜色。

本例要重新按条件算一遍：B 是否真的超成本，A/C 是否符合门槛，C 是否在合格候选里具有更高的示例成功率；再确认图和表没有用不同口径，页面没有把“建议继续测试”写成“效果已验证”。

**本例产出**：一份可交付的成稿，以及真实的检查记录。没有在手机或 PDF 中看过，就保留“未验证”，不能用桌面截图替代所有媒介的验收。

## 五、第二层：表达库——用什么，怎么组合

表达库包含可以独立使用的组件，也包含多种组件共同完成一个阅读任务的组合方式。它不是一个“看到某个关键词就套模板”的图形菜单。

### 1. 先选表达形式

| 读者想做什么 | 优先考虑 | 为什么这样选 |
|---|---|---|
| 理解一句判断、原因或限制 | 文字 | 把条件和逻辑讲完整，比装饰性的图更直接 |
| 查准确数值、比较多个字段 | 表格 | 相同字段对齐，便于逐项核对 |
| 看数量差距与排序 | 条形图、点图 | 用位置或长度比较量值 |
| 看随时间或连续输入的变化 | 折线图 | 保留顺序和真实间距，能看出趋势与断点 |
| 看数据集中在哪、分散多大 | 直方图、箱线图等 | 分布信息不能只靠一个平均数代替 |
| 看变量关系或群体差异 | 散点图、矩阵等 | 展示共同变化、分组和离群点；相关不自动等于因果 |
| 看整体由哪些部分构成 | 堆叠图、矩形树图（Treemap）等 | 先核对部分能否加总、整体如何定义 |
| 看区间、误差或不确定性 | 误差线、区间图、置信带等 | 明确区间是什么，而非给点估计加装饰阴影 |
| 理解步骤、条件、对象关系 | 流程图、架构图、关系图 | 让方向、分支、包含关系有明确含义 |
| 理解概念、主题或气氛 | 插画 | 帮助建立印象；不承担精确数据或执行逻辑 |
| 探索输入变化后的结果 | 有必要的交互 | 只有当操作能帮助理解问题时才加入 |

这个表是入口。具体统计方法和边界见[选图判断树](../references/2026-10-04%20-%20选图判断树.md)与[图表选型](../references/2026-10-03%20-%20图表选型与绘制.md)。

本例选表格，因为读者要同时核对不同类型的字段。若问题改为“哪个成本最低”，成本条形图会更直接；若问题改为“提高预算后候选怎么变化”，才可能需要预算输入控件。

### 2. 再选组件与组合

| 组件 | 负责什么 | 本例如何使用 |
|---|---|---|
| 输入与引用块 | 区分外部原文、题目和输入条件 | 展示本次比较规则，避免被误读成测量结果 |
| 指标组 | 快速呈现少量关键量 | 必要时概览样本量和成本上限；不取代完整比较 |
| 比较表格 | 保留字段与对象的对应关系 | 同时呈现三个方案的表现和成本 |
| 代码块 | 展示可读取、可复制的代码 | 只有需要解释计算或复现时加入 |
| 提示与结论框 | 提醒读者注意判断、限制或下一步 | 说明优先测试 C，并紧邻成立条件 |
| 状态标签与反馈 | 说明业务状态或操作结果 | 用“下一轮待测试”等明确文字；不把推荐当作成功 |

“方案比较”是一个组合：输入条件、比较表、推荐结论和限制说明共同回答同一个问题。另一个“风险审阅”组合可能使用风险摘要、代码片段、评论和待办，不能因为都属于 HaosuNaki 就长成同一种页面。

### 3. 基础样式、组件、组合、页面的区别

![把零散内容组合成有主次的完整页面](images/composition-collage.png)

先按阅读任务把内容分组，再安排先后和主次，最后统一样式。这张插画表达的是“组织与组合”，不是需要照抄的页面模板。

| 组成层次 | 是什么 | 举例 |
|---|---|---|
| 基础样式 | 可共用的视觉参数 | 字体、颜色、字号、间距、线宽 |
| 组件 | 可以单独说明用途与行为的小单元 | 比较表、引用块、代码块、状态标签 |
| 组合 | 一组组件共同完成一个阅读任务 | 条件 + 比较表 + 建议 + 限制，完成方案比较 |
| 页面 | 安排完整的阅读过程 | 背景、核心结论、证据、机制、下一步 |

组件可以替换，组合也可以因内容调整。但替换后仍要完成原任务。例如，把表格换成卡片，如果导致相同字段无法对齐，便损害了比较能力；看起来更丰富并不代表表达更好。

### 4. 两种连线图，三种交互

**执行型流程图**帮助读者照图办事，例如审批、排查和操作流程。真实条件用菱形，条件分支、起止范围和异常路径要清楚。连线尽量短、水平或垂直；菱形从顶点进出，同一顶点只出一条线。

**解释型轻量图**帮助读者理解机制，例如输入经过几个模块形成结果。保留必要关系，减少次要细节，留出呼吸空间。两种图都可以进入正式稿，选择依据是读者任务，而不是哪一种看起来更正式。

节点的调试编号用于评审定位，正式稿默认移除；真实业务编码和完整对象名称保留。总览加局部展开时，要让读者知道放大的是同一个环节，不能把展开引线画成流程箭头。

交互也要分清三种：

- **查看详情**：展开注释、查看某个数据点。不会改变数据。
- **切换视角**：筛选分组或切换比较方式。要保留对象身份和比较口径。
- **改变输入并计算**：调整假设，得到新的情景结果。必须先明确输入、公式、结果和解释，并同步更新图与文字。

第三种交互的结果应写成“在这些假设下计算得到”，不能冒充新的实测或未来一定发生的结果。

## 六、第三层：视觉映射——同一种风格，不同内容有不同待遇

视觉映射，就是把内容的重要性、归属和状态，转成读者看得出来的区别。它不等于给所有东西统一换成蓝色，也不等于把字号和间距设成同一个值。

### 1. 先分清身份、强调和状态

| 本例中的内容 | 属于什么 | 应当怎样理解 |
|---|---|---|
| 方案 C | 对象身份 | 在不同图里仍然是同一个方案 |
| 推荐优先测试 C | 内容强调 | 当前讨论的重点或建议 |
| C 下一轮待测试 | 业务状态 | 下一轮测试尚未开始 |
| 当前界面选中 C | 交互状态 | 用户正在看或操作 C |

这四种含义不能用一个蓝色高亮后就视为相同。状态需要文字、符号或必要的线型配合；仅凭颜色，读者容易把“推荐”误读为“已经成功”。

### 2. 颜色先服务含义，再保持风格

颜色判断顺序是：**先满足业务含义与阅读区分，再选择合适的主题颜色。**

- 有明确领域约定时，先采用对应约定。例如本体系面向红涨绿跌语境的蜡烛图采用该含义；面向其他市场时明确当地约定与图例。
- 多个对象需要同等识别时，采用区分度足够的类别色。同一对象跨图保持同色，不能按每次排序重新分配。
- 只强调一个对象、且没有既定类别或领域色义时，才使用“主要对象蓝、其他对象灰”等重点模式。已有类别色保持不变，改用标注、边框或线宽强调。平等比较不能默认把大部分对象弱化。
- 表达从少到多的量值时，用有顺序的色阶；表达相对基准的正负差异时，用发散色阶并说明基准。缺失不当零，冷暖也不能自动解释成好坏。

默认纸白、钴蓝、陶珊瑚等提供共同气质。需要更大的类别区分或明确冷暖关系时，可以使用更合适的颜色，不能为了品牌一致牺牲理解。

### 3. 字号和密度由内容职责决定

正文要适合持续阅读；表格、图注、代码、标签要适合快速定位。因此，它们可以使用不同字号和行距，不能让小字说明与正文完全没有层级，也不能把所有组件都放大成长文正文。

当前默认字体分工：中文标题 Songti SC，中文正文 PingFang SC，英文标题 IBM Plex Mono，英文正文 JetBrains Mono，独立数字 Georgia。日常生成沿用这套分工；若明确要定制主题，可以更换，但要同时检查回退、许可和版面变化。

长文参考尺度为中文桌面 20px / 36px、英文桌面 19px / 32px，手机分别为 19px / 34px、18px / 30px。组件和图内文字另按职责安排；这些数字不能不顾实际显示宽度直接套到所有图上。

### 4. 用归属关系决定边界、对齐和留白

同一模块内部应紧凑，模块之间应容易分开。标题、图例和备注都属于图的一部分，不要把它们推到很远的位置。必要时用浅底、分隔线和间距共同说明归属，避免“大框套小框”而没有意义。

长文通常沿稳定阅读列排列。确实需要更宽的表格或图形时，让同组标题、控件、图和图注一起展开；不要在一段阅读过程中突然宽、突然窄。

本例是混合字段的比较表，表头、文字和数值共用清楚的左轴。对于纯数值列，可以让表头与数值一起右对齐。**数字使用 Georgia，不代表数字必须右对齐。**

机制图的普通节点用白底，与纸白页面分开；只给明确强调的节点或分组增加色彩。节点正文在完整形状内居中，临时标识不挤占正文行。

### 5. 主题可以替换，内容判断不能被替换掉

Tokens 可以理解成一份有名字的设计参数表。例如“页面底色”“主要文字”“强调边界”分别有自己的参数，页面和图形工具从同一处读取。

换主题可以改变字体、配色、间距和线条，但不能改变本例的成本上限、成功率、筛选规则和推荐依据。强调色和类别色即使碰巧使用相同色值，也仍然是不同职责。

当前实现需要修改参数后重新生成。已经导出的 HTML、SVG 不会自动换肤；复杂图的坐标、换行和插画也不会随主题自动完成调整。换主题后仍然需要验收。

## 七、第四层：验收规则——怎样知道做对了

验收从任务开始时就参与判断。知道最终要检查什么，才能在前面保留必要字段、单位、条件和来源。

| 检查面 | 要问的问题 | 本例怎么查 |
|---|---|---|
| 内容 | 原意、条件、证据和未知有没有保留？ | 成本门槛是否仍是 1.2；建议是否只针对下一轮测试 |
| 数据 | 数字、分母、单位、排序和缺失是否正确？ | 68/100 是否是 68%；三组是否使用同一口径 |
| 表达 | 选用的图和组件能回答问题吗？ | 只看成功率条形图会遗漏成本，所以保留比较表与条件 |
| 视觉 | 重点、归属、类别和状态能否区分？ | “推荐 C”和“C 下一轮测试已完成”是否有明确区别 |
| 操作 | 按钮、筛选和计算是否兑现承诺？ | 如果有预算输入，候选、图表和结论是否同步更新 |
| 媒介 | 实际阅读、下载和打印是否可用？ | 桌面与窄屏能否读清；下载文件是否完整 |

**测试通过和成品验收不是一回事。** 程序检查可以证明某些输入按规则处理，不能证明长标题没有碰撞、手机文字够大、PDF 没有截断。需要在实际交付形式里打开查看，涉及交互时还要实际操作。

发现问题后，按原因返回：

| 发现的问题 | 回到哪里 |
|---|---|
| 不知道为什么推荐 C，或条件本身不明确 | 决策流程：重新明确目标与规则 |
| 看不出不同方案的字段对应关系 | 表达库：调整表格或组合方式 |
| 类别颜色太接近，说明离主体太远 | 视觉映射：改配色、归属和间距 |
| 计算错误、遗漏样本或错误连线 | 回到材料整理或实现，纠正内容与计算 |
| 手机标签重叠、下载后缺说明 | 调整布局或导出实现，再检查实际文件 |

交付时应说明哪些检查已经做过、哪些没做。对未验证事项诚实说明，是这套体系的一部分。

## 八、同一个例子，最终会长成什么样

按上面的判断，本例可以组织成以下阅读顺序：

1. **先给建议**：按本次规则，优先继续测试 C。
2. **紧接条件**：成本不超过 1.2；在合格候选中比较本次成功率。
3. **展示证据**：保留成功次数、任务数、成功率和成本的三方案比较表。
4. **解释取舍**：B 示例成功率最高但成本超限；A/C 合格，C 在这批数据里更高。
5. **说明边界**：合成示例，未证明统计显著性，也没有覆盖所有性能维度。
6. **给出下一步**：继续收集实际任务数据，再判断结论能否稳定成立。

这不是要求每篇文档都按六段排版。换成事故复盘、产品方案或机制说明，组合会变化；稳定的是“先判断读者问题，再组织证据和表达”的方法。

反馈时也可以直接指出问题所在：

```text
这一页先让我看到结论，再给依据。
表格里的同一字段没有对齐，比较起来费力。
这张图是平等比较，不要只突出一个方案。
流程中遗漏了失败分支，先补逻辑再改样式。
换一个更安静的主题，但保留原有数据和判断规则。
```

## 九、安装与实际操作

不需要懂 Python 才能向助手调用这套方法。技术命令主要供需要自行运行或维护的人使用。

### 安装为 skill

下载完整仓库，保留 `SKILL.md`、`references/`、`assets/`、`scripts/` 的相对位置。按照所用助手的说明，把完整目录放入个人 skill 目录，形成 `skills/haosunaki/SKILL.md`，再按宿主方式启用。

若已存在同名目录，先备份并比较差异，不直接覆盖。只复制 `SKILL.md` 会缺少脚本和资源；安装 skill 也不会自动增加图像生成、浏览器控制或 PDF 导出能力。

### 查看示例与生成 HTML

将[本说明书 HTML](manual.html)或[示例 HTML](../examples/demo.html)下载后，用浏览器打开。GitHub 文件页不会执行 HTML 或其中的 JavaScript。

运行要求为 Python 3.10+；核心脚本只使用标准库。发布时已执行的本地测试环境为 Python 3.12.14。重新生成示例：

```sh
python3 examples/build_demo.py
```

制作自己的页面，先把正文保存为带 `<main>…</main>` 的 UTF-8 HTML 片段，再构建：

```sh
python3 scripts/build_html.py \
  --body body.html \
  --title "方案说明" \
  --output report.html
```

构建器负责合入样式、所需脚本、开源字体与许可，**不会替你理解初稿并自动生成内容**。前面的判断与正文编写，由使用 skill 的助手或作者完成。

输入与输出不能是同一文件，默认拒绝覆盖已有输出；确需覆盖目标文件时使用 `--force`。正文中的外部图片和脚本不会自动被下载内嵌，离线交付需要另外核对资源。正文应来自可信材料，构建器不是安全清洗工具。

### 生成图形与修改主题

本版可直接用新数据生成的基础工具有三个：`bar()` 条形图、`line()` 折线图、`flow()` 显式坐标机制图。完整接口见[图形工具说明](../references/2026-10-04%20-%20图形工具接口.md)。复杂统计、空间投影、复杂机制布局和交互需另行实现与验证。

[67 项官方参考索引](../references/2026-10-04%20-%20已确认图族与复用索引.md)帮助理解不同表达的用途，不等于 67 个通用生成器，也不包含可随意再发布的官方图稿。

主题参数位于 [design-tokens.json](../assets/design-tokens.json)。修改后校验并重新生成：

```sh
python3 scripts/design_tokens.py --check
python3 scripts/design_tokens.py --mapping
```

这里的 Tokens 是本项目的轻量格式，不承诺完整兼容 DTCG。主题参数的具体范围见[参数维护说明](../references/2026-10-05%20-%20设计Tokens与参数维护.md)。

核心检查命令：

```sh
python3 -m unittest discover -s tests -v
```

## 十、插画、输出与许可

插画用于概念、气氛和隐喻；精确数据、执行逻辑和系统关系继续用对应图表。正文默认用 **A 细线编辑**，封面和大幅开篇可用 **C 纸感拼贴**。不要求每页都有插画，同组图片保持风格一致。

公开版提供[插画规则与提示词](../references/2026-10-05%20-%20插画风格与生成.md)，实际生图依赖宿主工具，不含历史参考 PNG，也不保证逐像素一致。

| 输出 | 适合什么 | 需要单独检查什么 |
|---|---|---|
| HTML | 图文阅读和交互探索 | 实际浏览器、窄屏、控件和离线资源 |
| PDF | 固定版面阅读与分享 | 分页、截断、字体、图注和打印尺寸 |
| GitHub README | 文字和静态图，链接其他产物 | 链接和图片可读性，不依赖页面交互 |
| SVG | 可缩放的静态图形 | 标签、边界、字体与实际显示尺寸 |

HTML 构建命令不直接生成 PDF。SVG 和 PDF 不保留完整网页交互，图外说明也不会自动进入导出的图形。输出形式改变后，需要重新检查。
